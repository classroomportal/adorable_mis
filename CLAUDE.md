# Formwork — orientation for Claude

School MIS for Adorable British College (Next.js 14 App Router + Supabase). Live app at `misform.work`, deployed on Vercel.

## Schema: read `sql/CURRENT_SCHEMA.md` before guessing

**A large part of this schema was built directly against the live Supabase instance and was never committed to `sql/` or `migrations/`.** Those two folders are an incomplete, roughly-chronological history — they are not a reliable source of truth for what currently exists. `sql/CURRENT_SCHEMA.md` is a full introspected dump of the live database (tables, columns, RLS policies, triggers, views, functions, extensions, cron jobs), fully regenerated 30 September 2026 (after migration 275) via the Supabase MCP connector. Check it before assuming a table/view/function doesn't exist, or guessing at its shape — several real incidents this session came directly from not doing that (see that file's intro for specifics: a PII-leaking view, an undocumented trigger that emailed real staff, etc.). Regenerate it (don't hand-edit) when the schema has drifted meaningfully.

`docs/SYSTEM_RULES.md` is a plain-English description of what the system does and the rules it enforces (who can do what, windows, limits, known gaps), written for school leaders. Keep it in step when a migration changes a rule it describes.

**Living documents: the Functional Specification and the PRD.** Two Claude Docs on claude.ai are the master description of the product: [Formwork — Functional Specification](https://claude.ai/code/artifact/659cca3b-399b-425f-bb5f-8b23577d5714) (what the system does today, as numbered requirements, including the audit trail and known issues) and [Formwork — Product Requirements (PRD)](https://claude.ai/code/artifact/d7ffd5d9-797b-4db0-b4b9-01f122498f7b) (goals, prioritised requirements, roadmap). `docs/FUNCTIONAL_SPEC.md` and `docs/PRD.md` are exported snapshots; never edit them by hand. A third Claude Doc, [Formwork — User Manual](https://claude.ai/code/artifact/419e765d-009a-414f-9da4-d81b2dd75894), is the staff/student/parent how-to guide with screenshots (taken from a copy of the app on invented data, never real students); `docs/USER_MANUAL.md` is its exported snapshot, with the screenshots in `docs/manual-images/`. That snapshot is also the in-app **Help** panel for staff (the "? Help" button in the top bar, `app/components/HelpButton.js`): `scripts/build-help.js` builds `public/help/` from it before every build and `next dev` (generated, git-ignored), and `lib/helpTopics.js` maps each page to its manual sections. Students and parents don't get the button. When the user says "update PRD and FS" (FS = Functional Specification), "update docs with changes" or anything like it (or a change alters a rule they describe), follow `.claude/skills/update-docs/SKILL.md`, which has the doc ids and the steps.

`sql/schema.sql` is the *original* bootstrap schema from early in the project — kept for history, not current.

## Getting live database access in a fresh session

There's an official Supabase MCP connector connected to this account (project ref `drjtcegtucovhbyfdpbx`, "adorable_mis"). If its tools (`mcp__Supabase__*`) aren't showing up via `ToolSearch`, it's usually just toggled off for the current chat, not actually disconnected — check `ListConnectors`; if `connected: true` but `enabledInChat: false`, ask the user to flip it on in that chat's connector settings, no need to redo any OAuth. Direct `psql`/raw Postgres connections are blocked by this sandbox's network policy — don't waste time on that path.

When the connector genuinely isn't available, the fallback (used successfully many times this session) is: write the migration as a numbered file under `migrations/`, paste the equivalent raw SQL into the chat in a code block, and have the user run it in the Supabase SQL editor.

## Conventions

- **Every migration that creates a table in `public` must also grant it to the API roles**, in the same file, right after enabling RLS — e.g. `grant select, insert, update, delete on public.new_table to authenticated;`. From 30 October 2026 Supabase stops doing this automatically for new tables, and a table without a grant returns "permission denied" to the app however its RLS policies are written. Grant `authenticated` only (the app is staff-login-only); add `anon` solely for something that must work before sign-in. Grant only the verbs the table's policies actually allow. Don't restore the old behaviour with `alter default privileges` — explicit per-table grants are the intended pattern, and RLS remains what decides which rows a user sees.

- Migrations are numbered sequentially in `migrations/*.sql` (currently up to 362), lowercase SQL, with a comment header explaining *why*, not just what. Follow the existing house style. Don't add `a_backup_mode_guard` triggers to new tables yourself: the `guard_new_tables` event trigger attaches one to every new `public` table automatically, and a second `create trigger` fails the migration (it did in 278).
- The `staff_demo` training account has been **removed** — there is no practice/demo login on the product anymore. Migrations 074–086 and `sql/CURRENT_SCHEMA.md` still document the `is_demo_account()`/`is_demo` mechanism from when it existed; treat those as historical, not current behaviour, and don't build new features assuming a demo account is reachable. If it's reintroduced, it needs a fresh design pass rather than resurrecting the old isolation mechanism as-is.
- `staff_roles.role_name` values in use: `admin, smt, hr, pastoral, houseparent, head_of_boarding, assessment_manager, assessment_user, teacher, bursar, school_office, admissions, tuckshop, tuckshop_owner, head_of_department, mentor, nurse, other_half, principal, college_secretary, attendance_officer`. `principal` and `college_secretary` (migration 259) approve fee prices. `attendance_officer` (migration 310, guardian.counselling@) gets the office missed-lesson pop-up (309) and Missed Lessons (307–308). `tuckshop_owner` (migration 229, cs@) is the only role that can unlock a saved hand-out list at `/tuckshop/hand-out`; `unlock_tuckshop_handout()` checks `staff_roles` directly, so being admin is not enough.
- Nova-T imports resolve a class's subject **only** through `subjects.subject_code`, matched against the group code's suffix with the set number stripped (`10LI/El` and `12a/El1` both reduce to `El`). `subject_code` is not editable from `/admin/subject-settings` — it is maintained by hand in SQL, so when adding a subject that will appear in a Nova-T export, set it to the code exactly as Nova-T writes it. The original import (`sql/013`) invented subject names by *guessing* what each code stood for and got `El` wrong — it expanded the school's Literature code to "Electronics" (see migrations 117–118). Before trusting any subject that import created, check it against who teaches it and where. Don't re-derive subject names from codes; the codes are the school's, not guessable.
- **The Other Half (OH) is run in Formwork, not Nova-T** (migration 156, `/other-half`). Activities, rooms, staff, year eligibility and student choices live in `other_half_*` tables, never in `classes`/`timetable_slots`, so a Nova-T import can't touch them — and the importer skips any `Oh`-coded group outright. OH registers write to `attendance` at the OH period (find it by `short_label = 'OH'`, not by number) with `other_half_activity_id` set. Students choose through `choose_other_half_activity()`, which enforces the choice window, year group and capacity. Nova-T's whole-year OH groups (`7a/Oh1` etc.) and Sports Academy groups (`77/Sa1` etc.) were deleted by migration 158 and the importer skips both `Oh` and `Sa`: Sports Academy is an OH activity students choose, not a class. Timetables show a student's chosen activity in the OH slot. **A group can be placed in an activity and locked** (migration 302, from the group's page): `place_group_in_other_half()` / `unlock_other_half_choices()` (allowed to `can_place_group_in_other_half()`: OH managers and group managers). `other_half_choices.locked` / `locked_until` (inclusive; null = until unlocked) are checked by `choose_other_half_activity()` and `drop_other_half_choice()` through `other_half_lock_in_force()`; `locked_by`/`locked_at` are stamped by a trigger. When a lock ends the placement stays. Students and parents see only "Placed by the school", never the reason; keep it that way. `registers_not_done` includes outstanding OH activities (migration 157): those rows have `slot_id` and `staff_id` NULL and carry `other_half_activity_id` — filter a person's rows on `staff_ids`, not `staff_id`.
- **A lesson can have its own teacher and room** (migration 182): `timetable_slots.staff_id` / `room` are set only where Nova-T gives one lesson someone or somewhere other than the class (`classes.staff_id` / `room`) — e.g. 8A1/Hu is LEE's class but one lesson is VAE's. NULL means "the class's"; `room = ''` means no room. Read them through `lib/lessons.js` (`loadStaffLessons`, `lessonTeacher`, `lessonRoom`), never the class's teacher/room alone, or you'll invent clashes and chase the wrong teacher for registers. The UPN/Class import also removes enrolments the export no longer lists.
- Almost nothing goes through `app/api` — pages talk to Supabase directly from the client. Business logic that needs to be trustworthy lives in Postgres functions/triggers, not in app code.
- **Every server route must check who is calling it, first.** Each HTTP handler in an `app/**/route.js` must open with `const auth = await requireResource(request, '<resource_key>'); if (auth.denied) return auth.denied;` from `lib/serverAuth.js`, before reading the body, env vars or anything else. Use the resource key of the page that calls the route (an array if several pages share it), or `ADMIN_ONLY` for actions that must stay admin-only whatever `/admin/permissions` says. Pages call routes through `apiPost()` in `lib/apiFetch.js`, which sends the sign-in token; a bare `fetch()` is refused. Never use the service-role key in a route. `scripts/check-api-auth.js` runs before every build (`prebuild`, which Vercel runs too) and fails it if a handler is missing the check, is written in another form, or if Server Actions (`'use server'`) or `pages/api` appear. Don't weaken the script or add to its `PUBLIC_ROUTES` list without the user's explicit agreement. Until this was added (Sept 2026) the two AI comment routes had no check at all, and anyone could call them on the school's Anthropic account. `RequireAuth`/`RequireResource` on pages are for display only, never the security boundary.
- **The one route without sign-in is the parents' calendar feed** (`app/api/calendar-feed/[token]/route.js`, migration 274, agreed by the principal 30 Sept 2026), because calendar apps can't sign in. It is in `PUBLIC_ROUTES`; the secret per-parent token (`parent_calendar_feeds`, only via `my_calendar_feed_token()` / `calendar_feed_events()`) is the check, it returns nothing once none of the parent's children is active, and it carries only parent-visible events (no `teacher_assessment`/`report_period`). Keep it that narrow; don't add more data to it.
- **The database decides who someone is, never the browser.** Any request can be copied from the Network tab and edited, so: every RLS policy and every `SECURITY DEFINER` function must identify the caller through `auth.uid()` (or helpers built on it: `is_admin()`, `user_has_staff_role()`, `has_resource_access()`, `teaches_student_for_subject()`…), and must treat any student/staff/parent ID or "created by" value in the request as a claim to check, not a fact. A new `SECURITY DEFINER` function either checks the caller first or has `revoke execute … from public, anon, authenticated` in the same migration (for cron/trigger-only helpers). Insert policies must pin the fields a user mustn't set themselves (e.g. an appeal's `status = 'pending'`). "Who did it" columns are stamped from `auth.uid()` by the `stamp_actor()` trigger (migration 214); add it to any new table with such a column. Migration 214 records the site-wide review of this and the gaps it closed; don't reintroduce them.
- **Deliberately open to all staff (the school's decision, 27 Sept 2026, not a gap):** any member of staff can edit subject aliases and subject key stages (ordinary ticks since migration 331) and can mark any register (`attendance`, an ordinary tick since migration 330), the principal, 3 Oct 2026. Security reviews shouldn't flag these or narrow them without asking. **Grade boundaries are no longer open to all staff:** only assessment managers edit them (the principal, 3 Oct 2026, migration 329), as a tick that admins can change.
- **Every grade change is logged permanently in `grade_history`** (migration 215): triggers on `results`, `target_grades` and `transcript_grades` record every insert, update and delete, including the old and new grade, the full old and new rows, and who did it (taken from `auth.uid()` and that user's `staff_id`, never from `results.staff_id` or `updated_by`, which the page sets). The table is append-only: update, delete and truncate are rejected by trigger, even from the SQL editor, and API roles have SELECT only. SMT, assessment managers and admins can read it. A new grade table needs the same `trg_log_grade_change` trigger. Never drop or disable these triggers to "fix" an import; bulk re-imports that change nothing aren't logged anyway. Viewed at `/assessments/grade-history`.
- **End-of-term exams are one result set per year group** (migration 246): "Y10 Term 1 Exam" etc., back to 2017 (Y7–Y8 that year, one more year group each year; Y12 from 2021–22, Terms 1 and 2 only, added by migration 252). Leavers' historic marks (up to July 2026) were loaded into these sets in Sept 2026 as `result_type = 'term_exam_import'`, percentages only. Find them by `calendar_events.exam_year_group` / `exam_term`, never by name; the same name recurs every year and all year groups of a term share a date, so marks in them must carry `result_set_event_id` (date matching is ambiguous). The KS3/KS4-5 transcripts (`lib/generateKeyStageTranscript.js`, grade choice in `lib/transcriptGrades.js`) read these sets first and legacy `transcript_grades` second. Scales: Y7–9 IGCSE only, Y12 WAEC only, Y10–11 both, so KS4/5 has an IGCSE and a WAEC version; WAEC for Y10–11 is worked out from the score via the subject's Year 12 grade boundaries.
- **Parents see only children still at the school** (migration 255, the principal's decision, Sept 2026). Leavers stay linked in `student_parent` (their parents were imported for the record), but `parent_read_own_links` shows a parent only links to `status = 'active'` students, via `my_current_child_ids()`, and every parent read policy joins `student_parent`, so a leaver's results, documents, fees, tuckshop and so on disappear from the portal too. A new parent read policy must join `student_parent` (or use `my_current_child_ids()`), never check `profiles.parent_id`/`student_parent` inside a `SECURITY DEFINER` function without the same status rule. Leavers' own student logins are locked (migration 251). Documents uploaded for leavers at `/reports/documents` are therefore staff-only.
- **Admissions** (migration 256, `/admissions`, design in `docs/admissions-and-year-rollover-design.md`). `academic_years` now exists ('2026/27' current, '2027/28' planning) and `terms.academic_year_id` is filled from `start_date`. Years are listed at `/admin/lookups`, added with `add_next_academic_year()`, re-dated with `set_academic_year_dates()` and removed (unused planning years only) with `delete_academic_year()` (migration 264); which year is `current` changes only at the year switch. Applicants live in `applicants`, never in `students`, until they are enrolled (phase 2, not built yet). An applicant's `status` and the fee, deposit, test-booking and decision fields can't be written by the app: `applicants_guard()` rejects them from `authenticated`. They only change through `book_admission_test()`, `post_admission_decision()` (admissions staff; it also produces and emails the matching standard letter), and `record_admission_form_fee()` / `record_admission_deposit()` (bursar only). The amounts themselves need two-person approval (below). 'tested' and 'interviewed' are set by triggers once the results are in. Applicant data is readable only with `/admissions` (admissions, SMT, admin); the bursar gets names and payments only, through `admission_fee_list()`. The pass mark (50% average of English and Maths) is `academic_years.admission_pass_mark`; each year group has its own paper (`admission_papers`). Letters are plain-text templates in `admission_letter_templates`, emailed with `email_reply_to('admissions')`; every letter produced is kept in `applicant_letters`. Applicants are kept indefinitely (the principal's decision), and changes are logged in `change_history` under `admissions`.
- **Fee prices are set and approved by the principal and the college secretary together** (the principal's rule, migration 259, `/bursar/fee-approvals`). `academic_years.admission_form_fee` / `admission_deposit` and `fee_items.default_amount` can't be written by the app (`guard_fee_prices()` rejects them from `authenticated`, including a new fee item created with a price). A change is a row in `fee_price_changes`, made by `propose_admission_fees()` / `propose_fee_item_price()` (bursar, SMT, either approver, or anyone with `/admin/lookups`), and applied only by `approve_fee_price_change()` once one holder of `principal` (principal@) and one holder of `college_secretary` (cs@), two different people, have both approved. Those two roles are checked in `staff_roles` via `holds_staff_role()`, so admin is not enough. Don't add another way to change these prices. **Locked items** (`fee_items.price_locked`: the tuition, activity, technology and medical categories, migration 260) are charged only at their approved price for the student's current year group (`fee_item_year_prices`, set by a `fee_item_prices` proposal via `propose_fee_item_year_prices()`, one approval per item covering Years 7–12), falling back to the item's approved single price. `enforce_locked_fee_price()` on `invoice_line_items` refuses any other amount however the line is added, whenever someone is signed in (migration 261); `price_locked` and a locked item's category can't be changed from the app. Damages, Tuckshop and discounts stay free. **Prices by year and term** (migration 343, `/finance/term-fees` on the Budget tile): `fee_item_term_prices` (item, `terms.term_id`, year group), written only when both approve a `fee_item_term_prices` proposal (`propose_fee_item_term_prices()`, `fee_price_changes.term_id`). `fee_price_for(item, year, term)` picks term price → year price → single price, and is what `enforce_locked_fee_price()` and the forecast use; charging finds the term through `fee_terms.term_id` ("1st Term" = September Term 2026, "2nd Term" = January Term 2027 (migration 349, not current or published yet); a new fee term must be linked or it keeps the year/single price). Year 12's Term 2 price covers Terms 2 and 3 (Term 3 is ₦0), the principal's rule. `fee_price_change_list()` is unchanged; Fee Approvals reads the term from `fee_price_changes`. The connector holds back `drop function` for confirmation too, so change a function's shape with a new function rather than drop/recreate through it. **Terms a fee is charged in** (migration 348): `fee_items.charge_term_ids` (school `terms.term_id`s; null = every term). `enforce_fee_item_term()` on `invoice_line_items` refuses a charge in another term (through `fee_terms.term_id`), and `budget_term_forecast()` leaves the fee out of other terms. A new fee is added in one call, `add_fee_item()` (name, fund, terms, prices sent for approval), from the numbered form `app/components/AddFeeForm.js` on `/bursar/fee-items`; the Fees & Bills tile is numbered 1 Fees … 10 Summary in process order. **New items are locked by category too** (migration 340, `trg_lock_fee_item_by_category`, after `trg_guard_fee_prices` by name): an item added with, or changed to, a category for which `fee_category_is_locked()` is true (tuition, activity, technology, medical, exam / exams / exam entry) gets `price_locked`, so it can have year-group prices and is charged only at its approved price; the app still can't send `price_locked` itself.
- **Detention, alert and certificate rules are data, edited at `/admin/lookups`** (migration 262). `behaviour_rules` (one row: the single-event and weekly-total detention thresholds, and the weekly alert threshold, stored as negative points) is read by `handle_negative_behaviour()`, `edit_behaviour_event()` and `notify_pastoral_on_negative_behaviour()`, and written only through `set_behaviour_rules()` (Lookups holders; it also saves `system_settings.detention_room` / `detention_time`). `certificate_levels` (name, points) drives `/certificates`; `certificates_awarded.level_name` records which level was given. Don't hard-code these numbers again. The "serious event" threshold (`serious_event_points`, migration 263: needs an explanation, and the office/SMT review before parents see it) lives there too; it is read by `edit_behaviour_event()`, `review_serious_behaviour_event()`, `review_behaviour_for_parents()`, and on the pages through `lib/behaviourRules.js` (`useBehaviourRules()` / `loadBehaviourRules()`).
- **Next year is planned in `plan_*` tables** (migration 265, `/admin/next-year`, phase 4 of the design doc). Setting up a planning year starts with its mentor structure (`plan_mentor_groups`, `plan_mentor_assignments`, confirmed with `confirm_mentor_structure()`); only then can its Nova-T timetable be imported, at `/admin/import-classes?plan=<academic_year_id>`, which points the same importer at `plan_classes` / `plan_timetable_slots` / `plan_curriculum_blocks` / `plan_student_class` (a trigger refuses plan classes until the structure is confirmed). Next year's class codes are the same as this year's, so **never import next year's Nova-T file without `?plan=`**: it would overwrite the timetable being taught. No live page reads the plan tables; the year switch (phase 5, not built) moves them into the live ones.
- **Only the school office can add a student** (migration 275, the principal's decision, 30 Sept 2026, after a test student was added to the live database by an admin account). `school_office_insert_students` is the only insert policy on `students`; admins can still read, edit and delete students, but admin alone can't add one. To stop someone adding students, remove their `school_office` role. That policy checks `has_staff_role()`, not `user_has_staff_role()` (which lets every admin through; migration 328 closed that). Don't add another insert route (policy, `SECURITY DEFINER` function or server route).
- **Who added a student is recorded** (migration 286): `students.created_at` / `created_by` are stamped by `stamp_student_created()` from `auth.uid()` on insert and can't be changed from the app afterwards. Null means added before 30 Sept 2026. **Names are tidied on save** by `tidy_name_columns()` (leading/trailing and double spaces, including non-breaking) on students, applicants, parents and staff; on `students` that trigger must stay after `trg_a_check_student_field_edit` alphabetically, or an edit to one field of a student with a badly spaced stored name would be refused as a name change.
- **Siblings are found through shared parents** (`student_siblings()`, migrations 267-272, the Siblings card on a student's profile, staff only, leavers included). `students.family_id` is empty for everyone, so don't rely on it. **Relationship is recorded per link** (`student_parent.relationship`, migration 272; `parents.relationship_type` is only the fallback for a link with none): principal@ and cs@ are linked to students they follow through the parent portal, and those links are "Other" (cs@ is Mother only for her own children, Daniel, Denzel and Jolie MBA). Two children are siblings through a parent only when neither link is Other. Keep that rule in any new sibling or family feature.
- **Homework** (migrations 278–279, `/homework`, design in `docs/homework-design.md`, the principal's decisions of 30 Sept 2026). `homework` is set per class. Subject, class code, year and academic year are copied from the class by `homework_prepare()`, never taken from the request. `homework_marks` are checked against the chosen `homework_schemes` by `homework_marks_check()`. Homework marks reach the end-of-term written report only through `homework_report_summary()` (below); transcripts, result sets, target grades and the Termly Grade Report never read them, and they are never written to `results`. Rules:
  - **Who writes:** `can_set_homework(class_id)` covers the class teacher, a single-lesson teacher, the HoD and admin, and only for classes listed in `homework_classes`. That table is the switch: since migration 353 (the principal, 4 Oct 2026; 295 had Years 10–11 only, after a pilot on 10_1/Ma and 11_1/Ma) it lists every Year 7–12 teaching class, i.e. not Mentor, Prep or Personal Study (`homework_is_teaching_subject()`). New classes are switched on automatically (migration 296, `trg_homework_switch_on_new_class` on `classes`, widened by 353): any class inserted as, or changed to, Years 7–13 with a teaching subject. It only ever switches on, and only when the year or subject really changes, so an admin's switch-off survives re-imports. `/homework` is granted to teacher, head_of_department and smt; the page shows a person's own classes (class or lesson teacher) as buttons and, in a drop-down, the other switched-on classes in the subjects they teach (view only: what was set, no grades or editing, the principal 1 Oct 2026) plus any they can manage (`my_homework_class_ids()`, one call: HoD, admin).
  - **Who reads grades:** `can_view_homework_marks()`, which is those people plus SMT. Not mentors, pastoral or assessment managers; `grade_history_read` hides homework rows from them too.
  - **Marks follow the student** (migration 291): a second select policy lets whoever teaches the student in that subject now (`teaches_student_for_subject()`) read all of the student's marks in that subject for the current academic year, from any class, so a class or teacher change doesn't leave them behind. `homework_marks.subject_id` (set by `homework_marks_check()`) is what it matches on.
  - **Reports** (migration 291): `homework_report_summary(report_period_id, student_ids, subject_id?)` gives per student and subject the average of the term's number-marked homework (any class, released or not; Not handed in counted separately, never as zero), its grade from the subject's boundaries for the student's year group, and counts. Callers see every student only if admin, SMT, `/reports/generate` or an assigned `report_checkers` row for that period (not the `/reports/check` page permission, which nearly every teacher has); otherwise only students they teach in that subject, or their department as HoD. The report writer shows it and pre-fills the Homework judgement (80/60/40 bands, `suggestedHomeworkJudgement()` in `lib/homework.js`, a starting value only); checkers see it; the printed written report shows **the grade only** ("Homework: B"), never the percentage, and a subject with no marks keeps the teacher's judgement (the principal's choice).
  - **Students** read through `my_homework()`: own grades only, once released, current academic year only.
  - **Late joiners** (migration 298): `student_class.joined_on` (default `school_today()`; enrolments that existed on 1 Oct 2026 are dated 1 Sept 2026). `my_homework()` and the students' homework read policy leave out homework due before the student joined that class, unless they already have a mark for it; the mark book, the class list's marked counts and the mark sheet leave them out of it too. Anything that recreates enrolments (an import that deletes and re-inserts) would reset the date, so keep enrolment updates as upserts.
  - **Parents** get nothing except the homework grade printed on a published written report. Don't add a parent policy or notifications without the principal.
  - Marks are logged in `grade_history` (`table_name = 'homework_marks'`).
  - **A mark becomes a grade** (migration 289): for mark-type schemes `homework_marks_check()` stores `grade` from `subject_grade_boundaries` (the homework's subject and year group; the highest band whose `min_score` the percentage reaches). A grade the page sends with a mark is ignored. In the mark book the drop-down holds only Not handed in / Excused for marked homework; the computed grade is shown beside the number.
  - **Files and links** (migration 281): `homework_attachments` plus the private `homework-files` bucket (`<homework_id>/…`, 20 MB, set file types). Rows are readable wherever the homework is. Files are readable only through a row (`homework_files_read`) and are opened by signed URL. Adding and removing is checked by `can_set_homework()` / `can_manage_homework_file()`. Add the row before uploading and remove the file before its row (`lib/homework.js`); otherwise a file is left that nobody can see or delete. Student hand-in is still not built.

- **Staff and students can sign in with their school Google Workspace account** (`/login`, migration 221). Google sign-in only ever *links* to a login Formwork already created (same confirmed email). `enforce_abc_domain_login()`, the BEFORE INSERT trigger on `auth.users`, raises on any new account whose provider isn't `email`, so an unknown Workspace or Gmail account gets no session at all. `/login` turns that error into "not set up in Formwork yet". Logins are only created by Formwork's own functions (`create_staff_logins` etc.), which insert email-provider accounts. Don't relax that trigger to let Google create accounts: several tables are readable by any signed-in user. The Google provider itself (client ID and secret, "Internal" consent screen, redirect URLs) is configured in the Google Cloud and Supabase dashboards, not in code. Parents still use email and password.
- **Before revoking EXECUTE on a function, find every caller**, including ordinary (non-`SECURITY DEFINER`) trigger functions, which run as the signed-in user and need the permission too. Then test each affected role's normal action, not just the attack. Migration 214 revoked `recalc_invoice_status()` without noticing `trg_recalc_invoice_status` called it as the bursar, and recording payments and fee charges failed for 40 minutes until migration 217 made the trigger `SECURITY DEFINER`.
- When building throwaway spreadsheets/exports for staff (HR rosters, boarding lists, tuckshop prices, etc.), pull live data via the Supabase connector rather than guessing — this repo's actual data has real quirks (placeholder rows, missing house assignments, initials-only names) worth surfacing to whoever asked.
- After finishing and committing a change, open a pull request for it rather than leaving commits sitting un-PR'd on a branch. Never merge a PR — even one you opened yourself — without the user's explicit go-ahead first.

## Running the app locally / building

`npm run build` (or `npx next build`) with `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` set — dummy values are fine for a build-only sanity check, real ones are needed to actually load data. `lib/supabaseClient.js` is sometimes swapped for a temporary mock during visual/screenshot testing (via Playwright + the pre-installed Chromium) — always restore it from a backup and verify `git status` is clean afterward before committing.
